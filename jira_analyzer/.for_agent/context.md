# Контекст проекта: jira_analyzer

## Суть
Пользователь работает в корпоративном аудите крупной организации
(название организации нигде не упоминать — ни в файлах проекта, ни в
публичных репозиториях: там за этим следят). Задача от руководства расплывчатая:
«проанализировать работу разработчиков» по данным Jira. Стратегия: собрать максимум
метрик модульно, нужные отобрать позже.
Только ~1.9% задач имеют дедлайны → метрики сроков не строят, факт зашит в отчёт.
Имена секций .env пользователя: JIRA_TOKEN и JIRA_DELTA_TOKEN (префиксы jira, jira_delta;
в config.py читаются суффиксы и _TOKEN, и _PAT).

## Среда
- Дома: Linux (разработка). На работе: **Windows** → всё должно запускаться на Win.
- Python 3.11+ (у пользователя 3.12). Библиотеки ставить можно почти любые.
- Авторизация: **PAT-токен** → заголовок `Authorization: Bearer <token>` (Server/DC).
- **ВАЖНО: на работе ДВЕ разные Jira** с разными PAT, структура полей примерно одинакова.
  В .env секции JIRA1_* / JIRA2_*, параметр «тип jira» передаётся вместе с именем проекта.

## Архитектура (согласована с пользователем, дружит с модульностью)
Пайплайн: fetch → parse/normalize → metrics → report. Модули общаются через файлы (кэш в data/).
1. **setup** — venv + установка зависимостей. Запуск дома напрямую `setup/start.py`;
   на Windows — `setup.bat` (установка) и `start.bat` (запуск web; python ищется
   по стандартным путям, не обязательно в PATH).
2. **fetch** — выгрузка задач: PAT из .env, имя проекта + тип jira на входе.
   JSON-конфиг с перечнем выгружаемых полей (наш «SELECT»). На выходе: файлы со статистикой
   задач + структура дерева epic→задача→подзадача (обсуждаемо). Папку результатов — путь в .env.
   Настройки в .env: задержка между запросами, ретраи на 429 с прогрессивной задержкой (+1с),
   диапазон дат задач.
3. **analysis** = 2 подмодуля: считать статистику / строить графики. Реестр статистик+графиков
   (декоратор-регистрация) → лёгкое добавление новых. Выбор, что считать, — настройкой.
4. **web** — FastAPI: форма (проект, тип jira, настройки), прогресс-бар (фоновое задание),
   выбор статистик, кнопка «скачать отчёт» (PDF/другое).
5. **core** — библиотека-оркестратор, общий для web-бэкенда и CLI (main.py).

## Тестовая площадка (дом, без auth)
- **CURATOR** — issues.apache.org/jira, Jira Server 10.3, 724 задачи, 18 подзадач,
  анонимное чтение API (v2). Запасные: RAT (583), ANY23 (574).
- Changelog читается анонимно (expand=changelog), статусы/авторы на месте.
- Epics в Apache-проектах отсутствуют (типы: Bug/New Feature/Improvement/Task/Sub-task) →
  epic-ветку дерева и ID custom field «Epic Link» узнаём через user_tests на работе.
- PAT Apache: selfserve.apache.org/jira-account.html — заявка возможна, но одобрение ручное
  (пользователь может отправить в фоне). Bearer-путь тестируем на рабочем PAT.

## Метрики (черновой список для шага 3)
активность создаётся/закрывается по неделям и людям; cycle time по статусам из changelog;
зависшие задачи; переоткрытия/возвраты; дисциплина (мимо статусов, без исполнителя);
комментарии; worklog; связь Confluence↔Jira (позже). Деликатность: считаем всё, в отчёт
выносим по согласованию.

## Решения по стеку
requests (сырой, прозрачнее обёртки atlassian-python-api из-за двух Jira) / pandas /
matplotlib / FastAPI / PDF: weasyprint или HTML→PDF. Финально закрепить в плане.

## Масштаб и форматы (решения этапа 1, 2026-11-12)
- На работе ~136k задач в проекте → всё заточено под большие объёмы:
  задачи пагинацией по 100 (page_size в конфиге), changelog батчами по 50 через
  search expand, задачи/чangelog пишутся потоково в JSONL (память O(страницы)).
- Комментарии выключены по умолчанию (--with-comments включает; модуль comments.py
  батч-режим) — метрики «общения» третий эшелон, пользователь подтвердил off.
- Тестовый прогон CURATOR: 724 задачи + 8523 события changelog = 19.5с дома.
  Экстраполяция на 136k ≈ 40–60 мин.
- Apache отключил /rest/api/2/issue/{key}/changelog → стратегия expand + догрузка
  урезанных (>100 событий) эндпоинтом, если он есть (на работе проверить probe'ом).

## Web (v2, финал)
- Результаты (таблицы + PNG-графики) рендерятся прямо в интерфейсе:
  /api/job/{id}/data + /api/job/{id}/fig/{stat}; скачивание HTML/Excel осталось.
- Спиннер/скрытие элементов — класс .hidden с !important В КОНЦЕ стилей
  (порядок CSS-правил его ранее побеждал — уже починено, не регрессировать).
- Графики к статистикам живут в src/analysis/plots.py; реестры в registry.py;
  рендер фигур защищён try/except (кривые данные не роняют задание).
- PDF-экспорт не реализован (осознанно, см. plan).

## Задача v5: разделение выгрузки и анализа в web (done 2026-11-13)
Решения, закреплённые навсегда:
- Скачал один раз — анализируй сколько угодно: web разделён на две зоны —
  «1 · Выгрузка задач из Jira» (POST /api/fetch, fetch-only задание) и
  «2 · Анализ скачанных выгрузок» (таблица + выбор строки → /api/run с
  skip_fetch=true). Галочка «анализ имеющейся выгрузки» удалена.
- Папки выгрузок плоские: data/raw/<КЛЮЧ_ПРОЕКТА>; тип jira, адрес, дата,
  счётчики — в fetch_summary.json (пишет fetch, читает GET /api/downloads).
  Легаси-папки без summary показываются с прочерками.
- Повторный fetch по тому же ключу = тихая перезапись (это «обновить»);
  если в папке выгрузка ДРУГОГО типа jira — confirm() в браузере. Никаких
  кнопок удаления/обновления (решение пользователя: руками).
- pipeline: run_fetch(opts) выделен, PipelineOptions.fetch_only — задание
  «только выгрузка» идёт через тот же механизм jobs.
- Имя проекта/папки санитизируется на POST-эндпоинтах
  (^[A-Za-z0-9][A-Za-z0-9._-]*$) — путь из него строится.
- CLI без изменений: --skip-fetch = то же самое руками; UI шлёт только
  project+metrics+skip_fetch (старые поля /api/run допустимы).

## Задача v4: параметры метрик (done 2026-11-13)
Решения, закреплённые навсегда:
- Метрика декларирует `params = [Param(...)]` (src/components/params.py: поля
  name/label/type number·text·date·select/default/placeholder/required/options/hint).
- Выбор пользователя = список экземпляров {metric_id, params}; одна метрика
  может встречаться несколько раз, порядок экземпляров = порядок в отчёте.
- Список метрик в web строго пуст при каждом открытии (без localStorage).
- Модалка строится фронтендом из декларации (/api/metrics отдаёт params);
  оверлей с blur, ⚙ у параметризованных, Esc/клик мимо/✕ закрывают.
- Валидация значений — backend, resolve_params(): дефолты, приведение типов,
  required/неизвестные/select-опции; ошибка = «упавшая метрика» (errors, v3),
  задание не роняется. opts.get("имя") в build() — значения уже чистые.
- CLI: `--metrics 'stale_issues(stale_days=45),overview'` (значения строками,
  типы приводит backend); --stale-days удалён, глобальный «Порог зависших» из
  web-формы удалён.
- params_label (краткая сводка значений) едет в MetricResult и показывается
  серым в заголовке карточки; тоже у ошибок (различение экземпляров).
- stale_issues: param stale_days (number, 14); activity_weekly/users:
  date_from/date_to (date, фильтр по created, tz-aware UTC, «по» включается).
- build_excel при нуле табличных блоков пишет пояснительный лист, а не падает.

## Задача v3: компонентная архитектура метрик (done 2026-11-13)
Решения, закреплённые навсегда:
- Метрика = компонент: .py-файл в metrics/ (класс-наследник BaseMetric), автоскан
  при старте, без декораторов. Старые registry/plots/stats удалены вместе с src/analysis/.
- Выход метрики = список BlockSpec (pydantic, дискриминатор type): table/bar/line/pie/list.
  Рендер единый: static/blocks.js используется И в web, И инлайнится в report.html.
- Рендеринг графиков: клиентский echarts (ECharts 5.6.0 вендорен в static/vendor/,
  1 МБ) везде — web и офлайн-отчёт; matplotlib полностью выпилен из проекта.
- Каждая карточка метрики в web сворачивается кнопкой до заголовка; отдельный блок
  может стартовать свёрнутым (collapsed: true в спеке).
- Папка плагинов: metrics/ в корне; инструкция для нейросети — metrics/README.md;
  тест-харнесс: python main.py --check-metrics (src/components/check.py, синтетика
  на random.Random(42) + структурные проверки блоков).
- Упавшая метрика не роняет задание: errors попадают в payload и показываются в web.
- «Скачать HTML» отдаёт attachment — браузер скачивает файл (пользователь подтвердил:
  файл падает в Downloads), офлайн-рендер проверен через /static копию.

## Задача v6: надёжный fetch — чекпоинты, возобновление, Стоп (done 2026-11-13)
Решения, закреплённые навсегда:
- Выгрузка пишется в data/raw/<КЛЮЧ>/_partial/ с чекпоинтом state.json после
  каждой страницы задач/пачки changelog/задачи догрузки; корень папки не
  меняется до полного успеха (упавший fetch не портит старую выгрузку).
- Возобновление — по явному выбору пользователя: web-баннер «Продолжить /
  Начать заново», CLI --resume/--fresh; без флагов при наличии прогресса —
  ошибка с подсказкой (web: 409). Отпечаток параметров (проект, jira_type,
  url, даты, max_issues, комментарии, hash fields.json) обязан совпасть.
- Кнопка «⏹ Стоп» (POST /api/job/{id}/stop) — статус stopped, прогресс
  сохранён; работает для выгрузок, не для анализа. Проводка стопа
  (opts.stop_event = job.stop_event в start_job) закреплена тестом.
- JSONL всегда читается «последняя запись по ключу выигрывает» (tables.py,
  commit-дедуп) — фикс двойного счёта событий у задач с >100 событиями
  (догрузка полной истории после урезанной). Офсеты чекпоинта — байтовые
  (файлы пишутся бинарно).
- Пагинация устойчива к лимиту глубины сервера (jira.search.max.results):
  пустая страница раньше конца total → деление диапазона по created
  рекурсивно (окна до 1 часа); проверено на Apache 10.3 (пусто за границей
  total отдаётся БЕЗ ошибки). Дедуп ключей сквозной. date_to включительно.
- Параллельные задания web НЕ ограничиваются — решение пользователя
  («на совести пользователя»); логи заданий разведены по потокам (фильтр
  по threadName), JOBS подрезается до 50 готовых.
- Зависимости — ограниченные диапазоны под Python 3.11–3.13 (pandas>=2.2,<3
  и т.п.; проверено на 3.12 с pandas 3.1.1); pydantic и numpy объявлены явно;
  dev-зависимости (pytest, httpx) — в requirements-dev.txt.
- Автотесты pytest в tests/ (44 шт, без сети): фейковый стенд Jira
  (conftest.FakeJira: пагинация, cap глубины, отказы, expand, /changelog),
  resume-цикл «падение → продолжение == цельный прогон», web API, reports,
  client-ретраи. Разовые скрипты — в .for_agent/test/, не в tests/.
- Эталон выгрузки CURATOR после всех фиксаций: 724 задачи, 8523 события
  (совпал с до-v6 прогоном) — data/raw/CURATOR.
