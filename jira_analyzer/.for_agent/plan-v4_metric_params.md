# План: v4 параметры метрик, запрашиваемые у пользователя

Статус: **done** (реализовано и проверено e2e 2026-11-13)
Дата: 2026-11-13

## Цель
Метрика декларирует параметры (Param) — web генерирует из них форму в модальном
окне; пользователь собирает отчёт из экземпляров метрик (id + значения параметров),
с настраиваемым порядком и повторным добавлением одной метрики с разными значениями.

## Принятые решения (шаг 1)
- Список метрик в web **строго пуст при каждом открытии** (без localStorage).
- CLI-синтаксис: `--metrics 'stale_issues(stale_days=45),overview'`;
  флаг `--stale-days` удаляется (порог становится параметром метрики).
- Глобальное поле «Порог зависших, дней» из общей формы удаляется — параметр метрики.
- Выбранные метрики = список экземпляров `{metric_id, params}` (одна метрика
  может встречаться несколько раз; порядок экземпляров = порядок в отчёте).
- Типы полей Param (расширяемо, как типы блоков): number / text / date / select.
- Валидация значений (типы, required, неизвестные ключи) — backend (resolve_params),
  ошибка параметров показывается как упавшая метрика (механизм errors из v3).
- На карточке метрики в web/отчёте — краткая сводка значений (params_label):
  «Зависшие задачи · порог: 45 дн» — различает экземпляры.

## Новый бэкенд
- `src/components/params.py`: `Param(name, label, type, default, placeholder,
  required, options, hint)` (pydantic) + `resolve_params(decl, values) -> dict`
  (дефолты, приведение типов, проверка required/неизвестных, текст ошибки по-человечески).
- `base.py`: `BaseMetric.params: list = []`; `MetricOpts` = {params: dict} с `opts.get(name)`.
- `pipeline.py`: принимает список экземпляров; для каждого — resolve_params →
  MetricOpts(params) → build; MetricResult получает `params_label`.
- `app.py`: `/api/metrics` отдаёт `params` каждой метрики; `RunRequest.metrics`
  = список `[{metric_id, params}]`.
- `main.py`: парсер `id(key=value,key2=value2)` в экземпляры; `--stale-days` удалён.

## Метрики (обновление)
- `stale.py`: param `stale_days` (number, default 14, required).
- `activity.py` (обе): params `date_from` / `date_to` (date, плейсхолдер
  «пример: 2025-01-01») — фильтр задач по created (tz-aware UTC).
- Остальные — без параметров (декларации пустые), поведение не меняется.

## Фронтенд
- Форма: блок «Метрики для отчёта» пуст; кнопка «Добавить метрику»; строка-подсказка.
- Модальное окно: оверлей (затемнение + backdrop-filter: blur), прокручиваемый
  <select> метрик, поля по декларации (number → спиннер, date → нативный календарь,
  text/select → поля; плейсхолдеры серым; дефолты предзаполнены), «Добавить»,
  крестик, клик по оверлею мимо окна, Esc.
- Список экземпляров: имя + сводка параметров, кнопки ↑ ↓ (граничные задизейблены),
  ✕; порядок = порядок в payload.
- blocks.js: `params_label` в заголовке карточки (серым после имени).

## Прочее
- `reports.py`: ничего структурного (params_label едет в payload сам; Excel-суффиксы
  «(2)» уже работают для повторов).
- `check.py`: MetricOpts без stale_days; прогон с дефолтными параметрами.
- `metrics/README.md`: новый раздел «Параметры метрики» + обновлённые примеры
  (stale — number, activity — date) + CLI-синтаксис.

## Итог (2026-11-13, отступления от буквы плана — только мелочи)
- Плюс `params_label` у ошибок: упавший экземпляр различим в списке ошибок
  web/отчёта («порог, дней: abc»).
- Фикс по пути: `build_excel` при нуле табличных блоков (все метрики упали на
  параметрах или вернули только графики) писал книгу без листов и ронял задание —
  теперь пишется пояснительный лист «Отчёт».
- `--list-metrics` показывает декларации параметров (`stale_days:number=14`).
- `validate_decl()` в params.py: имена/дубликаты/select-options проверяет харнесс.
- e2e web пройден в браузере: пустой список при старте, модалка (оверлей+блюр,
  ⚙ у параметризованных, поле с дефолтом и hint), две «зависшие» (45 и 400),
  стрелки (порядок меняется, граничные задизейблены), ✕ и повторное добавление,
  Esc, запуск — карточки в порядке списка с серыми сводками.
